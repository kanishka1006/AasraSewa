# ESP32 demo connection

The original README and IoT design documents specify MQTT, GPS, vitals and an SOS
button. They do not specify sensor models, GPIO pins or an existing firmware sketch.
`AasraMqtt.h` is a networking adapter for your sensor sketch, not a sensor driver.
No sensor readings are fabricated by this adapter.

## Running laptop services

The existing frontend, backend, MongoDB, MQTT and IoT ingestion must be running
(see `../../LOCAL-RUN.md`). A separate authenticated LAN gateway is now available:

| Setting | Current demo value |
| --- | --- |
| Host | `YOUR_LAPTOP_LAN_IP` (generated by npm run setup) |
| Port | `1884` |
| Username and password | Generated by setup in ignored `config.h` and root `.env.esp32` |
| Band ID | `00:1B:44:11:3A:B7` |
| Assigned wearer | Seeded citizen Rohan Gupta |
| Normal topic | `bands/00:1B:44:11:3A:B7/telemetry` |
| SOS topic | `bands/00:1B:44:11:3A:B7/sos` |
| Monitor | http://localhost:3002/admin/iot |

The gateway forwards only this band's telemetry and SOS topics to the internal
MQTT broker at `127.0.0.1:1883`. It requires credentials, denies subscriptions,
and rejects retained messages. It uses plain MQTT for a trusted local demo Wi-Fi;
use TLS and per-device credentials for deployment outside this local demo.

To restart the gateway from the repository root:

```powershell
npm run gateway
```

The ESP32 and laptop must be on a network where devices can reach each other.
Use the laptop's LAN address in firmware, not `localhost`. Campus/guest Wi-Fi
may isolate clients; a shared phone hotspot can avoid that restriction.
If the laptop changes Wi-Fi networks, update the host in `.env.esp32` and
`config.h`, then restart the gateway. Allow inbound TCP 1884 on the chosen
trusted network if Windows Firewall blocks the connection; the setup has not
modified firewall rules.

## Add the publisher to your sensor sketch

1. Install your ESP32 board support and **PubSubClient** by Nick O'Leary in Arduino
   IDE, or add the corresponding dependencies in your existing PlatformIO project.
2. Copy `AasraMqtt.h` and your local `config.h` beside your existing sketch.
3. In `config.h`, replace only `YOUR_WIFI_SSID` and `YOUR_WIFI_PASSWORD` with the
   Wi-Fi used by the board. Broker settings have already been filled locally.
4. Include and initialize the adapter:

```cpp
#include "AasraMqtt.h"
AasraMqtt uplink;

// Add to your existing setup(), after Serial.begin(...) and sensor initialization:
// uplink.begin();

// Call frequently in your existing loop(), without long blocking delays:
// uplink.loop();
```

After your sensors produce a valid GPS fix and measurements, send every 5 seconds:

```cpp
// These names represent variables in YOUR sensor sketch, not fixed sample values.
bool sent = uplink.publishReading(
    gpsLatitude, gpsLongitude, measuredHeartRate, measuredSpO2,
    measuredTemperatureC, measuredBatteryPercent, false);
```

On a debounced SOS button press, call the same function immediately with `true`
as the last argument. Supply `NAN` for optional vitals or battery that are not
measured; they appear as **Not reported**. Latitude/longitude and a synchronized
Unix timestamp are required. The adapter synchronizes time through NTP; it will
not publish until Wi-Fi, MQTT, time, and valid coordinates are available.

PubSubClient publishes at QoS 0, so `sent == true` is not proof of ingestion.
Confirm the packet timestamp and values in the monitor. This adapter does not
implement durable offline SOS queuing or application acknowledgments.

References: [Espressif Wi-Fi API](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/wifi.html),
[PubSubClient API](https://pubsubclient.knolleary.net/api.html).

## Packet contract

The running ingestion accepts the flat format below and the nested
`vitals.bpm`, `vitals.spo2`, `vitals.temp` fields in the original design document.
The following numbers are an example only; firmware must use measured values.

```json
{
  "ts": 1793250000,
  "lat": 28.6139,
  "lon": 77.2090,
  "hr": 72,
  "oxy": 98,
  "tmp": 36.6,
  "bat": 85,
  "sos": false,
  "source": "esp32"
}
```

`ts` is Unix **seconds**, not milliseconds. The full band ID in the topic must
match the registered band's `macAddress` and active rental. The seeded alias can
be used for this demo even if the board's physical Wi-Fi MAC is different.

## Verify the demo

1. Sign in at http://localhost:3002/login with `+919999999999` / `password123`,
   then open **IoT Monitor**. Tokens expire after 15 minutes; sign in again if asked.
2. Power the ESP32. Serial Monitor should report `Aasra MQTT connected`.
3. Confirm its row changes from **simulator** to **esp32**, timestamps advance,
   and displayed values match the sensor values printed by your sketch. The
   publisher label is supplied by the sender, not hardware attestation.
4. Move the device and verify the GPS coordinate changes. Packet polling is 3 seconds;
   tile imagery requires Internet access.
5. Press SOS. The monitor should show an active alert for Rohan Gupta and a red
   marker. Repeated SOS messages reuse the wearer's active alert. Release the
   button and click **Resolve** after the demo.
6. Disconnect the ESP32. After 15 seconds, its row should show **Stale**; the last
   known location remains visible. Reconnect and verify the timestamp advances.

The old Overview / Live Map screens and user-table battery display still contain
sample data. Use **IoT Monitor** to verify incoming packets.

To reproduce the software-only integration test from the repository root:

```powershell
node scripts/iot-demo.cjs --sos --resolve
```

It publishes explicitly labelled simulator readings, checks the authenticated
location API, verifies that a repeated SOS leaves one active alert, then resolves
that alert. Omit `--resolve` to leave the simulated SOS visible. Resolve existing
alerts before repeating a new SOS test. Do not run the simulator while validating
physical sensor readings for the same band.

The software integration test covers normal telemetry, SOS repeat handling and resolution
through both internal MQTT and the authenticated LAN gateway. ESP32 firmware
compilation, sensor wiring, Wi-Fi client reachability and physical measurements
remain to be verified on your board.
